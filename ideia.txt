Sim. Depois de pesquisar o ecossistema atual, **eu acho que existe um projeto open source interessante aqui**, mas eu mudaria um pouco a definição:

> **não criaria um “MCP de sotaques” nem uma coleção de prompts. Criaria um padrão + runtime open source para personas sociolinguísticas, começando pelo português brasileiro.**

A diferença parece pequena, mas transforma isso de “repositório de prompts engraçados” em infraestrutura reutilizável.

## A ideia que eu construiria

Internamente, eu evitaria tratar `baiano`, `paulista`, `sergipano` etc. como uma personalidade. Seria melhor chamá-los de **Regional Persona Packs** ou **Regional Style Packs**.

Isso permite separar coisas que não deveriam ser confundidas:

| Camada | Exemplo |
|---|---|
| Idioma | `pt-BR` |
| Região | Nordeste |
| Estado | Bahia |
| Localidade | Salvador |
| Registro | conversacional |
| Intensidade regional | leve / moderada / forte |
| Papel | vendedor |
| Domínio | automotivo |
| Marca | Honda |
| Regras da empresa | financiamento, concessionária, atendimento etc. |

Então um agente poderia ser composto assim:

```text
pt-BR
  + Bahia
  + Salvador
  + regionalidade: 0.35
  + atendimento-comercial
  + Honda
```

Enquanto Recife seria:

```text
pt-BR
  + Pernambuco
  + Recife
  + regionalidade: 0.35
  + atendimento-comercial
  + Honda
```

A inteligência comercial continua sendo exatamente a mesma. Só muda a camada sociolinguística.

Isso é **muito melhor** que manter `honda-baiano-prompt.txt`, `honda-pernambucano-prompt.txt`, `honda-sergipano-prompt.txt` etc.

# Por que eu não usaria MCP como núcleo

O próprio MCP separa `prompts`, `resources` e `tools`. Prompts são templates controlados pelo usuário; resources são contexto controlado pela aplicação; tools são capacidades executáveis que o modelo pode chamar. :chatgpt-content-reference{index="0"}

Para o seu exemplo da Honda, **não quero que o modelo decida se vai ou não “usar Bahia”**. A aplicação sabe que aquela concessionária está usando o perfil `br/ba/salvador` e deve aplicar aquilo deterministicamente.

Portanto eu faria:

```text
Persona Specification
        ↓
Persona Compiler
        ↓
Provider Adapter
        ↓
OpenAI / Anthropic / Gemini / local LLM
```

MCP seria apenas **uma interface opcional** posteriormente.

Por exemplo:

```text
persona://br/ba/salvador
persona://br/pe/recife
persona://br/se/aracaju
```

E um MCP poderia expor operações como:

```text
persona.list
persona.get
persona.render
```

Mas isso seria um produto do projeto, não seu formato fundamental.

# E Skills?

**Skills fazem bem mais sentido como formato de exportação.**

OpenAI hoje suporta Agent Skills e os define como diretórios com `SKILL.md`, instruções e arquivos auxiliares; além disso, a implementação é compatível com o padrão aberto de Agent Skills. :chatgpt-content-reference{index="1"}

Então você poderia ter:

```bash
personabr export br/ba/salvador --target openai-skill
personabr export br/ba/salvador --target claude-skill
personabr export br/ba/salvador --target system-prompt
personabr export br/ba/salvador --target mcp
```

É aí que acho que o projeto começa a ficar **bem interessante como open source**.

Uma persona, vários runtimes.

Eu criaria um formato declarativo.

Algo aproximadamente assim:

```yaml

  id: br.ba.salvador
  language: pt-BR
  country: BR
  state: BA
  city: Salvador
  version: 1.0.0

scope:
  type: sociolinguistic
  register: conversational
  default_intensity: 0.30

linguistic:
  vocabulary:
    preferred: []
    contextual: []
    discouraged: []

  discourse_markers: []

  morphosyntax:
    patterns: []

  pragmatics:
    greeting_patterns: []
    acknowledgement_patterns: []
    disagreement_patterns: []
    closing_patterns: []

  orthography:
    phonetic_spelling: avoid

style:
  rhythm: natural
  verbosity: moderate
  regional_marker_frequency: low

constraints:
  avoid_caricature: true
  avoid_stereotypes: true
  preserve_task_accuracy: true
  never_invent_regionalisms: true

  sources:
    - id: ...

  native_review_required: true
```

O interessante é que isso **não é o prompt enviado ao modelo**.

É a especificação.

O compiler transforma isso no melhor conjunto de instruções para GPT-5.6, Gemini, Claude etc.

Esse detalhe é fundamental.

# O erro que eu evitaria desde o primeiro commit

Não faça:

```yaml
baiano:
  relaxed: true
  humorous: true
  likes_to_talk: true
  uses_oxe: true
  uses_meu_rei: true
```

Isso rapidamente vira caricatura.

O projeto deveria descrever **fenômenos linguísticos observáveis**, e não presumir traços psicológicos das pessoas de uma região.

Inclusive, a própria pesquisa linguística mostra por que `baiano` é uma abstração excessivamente grande. O ALiB trabalha explicitamente com variação geográfica e multidimensional, abrangendo capitais e localidades do interior; pesquisas também mostram continuidades linguísticas que não respeitam simplesmente fronteiras estaduais, como entre Bahia e Sergipe. :chatgpt-content-reference{index="2"}

Portanto seria perfeitamente possível existir:

```text
br/ba/salvador
br/ba/recôncavo
br/ba/sul
br/se/aracaju
br/se/interior
```

e não simplesmente:

```text
baiano
sergipano
```

Isso dá **credibilidade acadêmica e técnica** ao projeto.

# Há dados para fazer isso seriamente

E foi aqui que achei sua ideia mais interessante.

O **Projeto ALiB — Atlas Linguístico do Brasil** existe justamente para descrever a diversidade do português brasileiro sob perspectivas geolinguísticas e dialetológicas. O planejamento atual envolve dados das 25 capitais pesquisadas e mais 225 localidades do interior. :chatgpt-content-reference{index="3"}

O histórico **NURC** trabalhou especificamente com fala urbana em Recife, Salvador, Rio de Janeiro, São Paulo e Porto Alegre, estudando dimensões fonético-fonológicas, morfossintáticas, lexicais, semânticas e estilísticas. :chatgpt-content-reference{index="4"}

Há ainda o **MuPe-Diversidades**, com amostras de fala e transcrições de diversos estados, incluindo Pernambuco, Alagoas, Sergipe e São Paulo. :chatgpt-content-reference{index="5"}

E surgiu recentemente o **Projeto SOTAQUE**, construindo um dataset aberto de vozes brasileiras com região, estado, cidade/microrregião e sotaque declarado; o projeto informa publicação sob CDLA-Permissive-2.0. Isso poderia se tornar particularmente interessante quando seu projeto evoluísse de **texto regionalizado para voz regionalizada**. :chatgpt-content-reference{index="6"}

Não significa automaticamente que todo material acadêmico desses projetos possa ser redistribuído: cada fonte precisaria ter sua licença verificada. Mas podem servir de base metodológica e bibliográfica para criação e avaliação dos packs.

# Existe concorrência?

Existe em **persona genérica**, sim.

O projeto **PERSONA.md / Personaxis**, por exemplo, criou uma especificação bastante sofisticada para definir identidade, caráter, personalidade, valores, cognição, voz e outras propriedades de um agente e compilá-las para diferentes plataformas. :chatgpt-content-reference{index="7"}

Também existem Character Cards e projetos como PersonaNexus. :chatgpt-content-reference{index="8"}

Por isso eu **não tentaria competir criando “mais um formato universal de personalidade de IA”**.

Sua vantagem seria:

> **uma especificação e uma biblioteca de localização sociolinguística para agentes.**

É muito mais específico.

E, pelo que encontrei, esse espaço está muito menos ocupado.

```text
├── personas/
│   └── pt-BR/

│       ├── pe/

│       └── sp/
│           └── sao-paulo/

├── packages/
│   ├── core/

│   ├── cli/
│   └── eval/
│
```

O primeiro adapter pode ser extremamente simples:

```ts
const persona = await loadPersona("br/ba/salvador");

const instructions = compilePersona(persona, {
  intensity: 0.35,
  register: "customer-service",
});

const response = await openai.responses.create({
  model: "gpt-5.6-luna",
  instructions,
  input: customerMessage,
});
```

Isso está perfeitamente alinhado ao modelo atual da OpenAI: `instructions`/developer messages são justamente onde ficam comportamento, estilo e objetivos de alto nível. :chatgpt-content-reference{index="9"}

Há um detalhe importante: quando se usa `previous_response_id`, as `instructions` da chamada anterior **não são automaticamente reaplicadas**. Seu adapter deve tratar isso corretamente e garantir a persona em cada execução relevante. :chatgpt-content-reference{index="10"}

Hoje, **29 de setembro de 2026**, a OpenAI está justamente recomendando que prompts de produção fiquem **versionados no código**, com testes, fixtures e revisão por Git, em vez de depender de objetos de prompt hospedados.

Os reusable prompt objects foram descontinuados e estão programados para desligamento em **30 de novembro de 2026**. :chatgpt-content-reference{index="12"}

# A parte que pode fazer esse projeto virar referência

Não são os YAML.

São os **evals**.

Cada regional pack deveria provar quatro coisas:

| Avaliação | Pergunta |
|---|---|
| Regional fidelity | A fala contém características compatíveis com aquela variedade? |
| Naturalness | Parece alguém falando normalmente ou uma caricatura? |
| Task fidelity | A regionalização prejudicou o atendimento? |
| Stereotype leakage | O modelo começou a inventar características culturais/comportamentais? |
| Overuse | Está enfiando regionalismo em toda frase? |
| Cross-model stability | GPT, Claude e Gemini produzem comportamento semelhante? |

E pessoas da própria região deveriam poder avaliar:

```text
parece natural
parece exagerado
não reconheço essa expressão
isso é de outra região
isso é ofensivo/caricato
isso realmente usamos
```

Aí nasce um dataset extremamente valioso.

Aliás, a OpenAI também está encerrando sua antiga plataforma hospedada de Evals e aponta migração para ferramentas como **Promptfoo**, então eu manteria os testes do projeto localmente/CI desde o início. :chatgpt-content-reference{index="15"}

```bash
vernaculo eject pt-BR/ba/salvador
```

`eject` seria particularmente legal:

```bash
vernaculo eject pt-BR/ba/salvador
```

Ele joga tudo para dentro do projeto e remove até a dependência do pacote Vernáculo.

**Zero lock-in.**

O Vernáculo não precisa ser apenas:

No futuro:

```text
pt-BR/ba/salvador

en-US/ny/new-york
en-US/tx
en-GB/london

es-AR/buenos-aires
```

Depois até registros:

```text

```

Por isso **Vernáculo** funciona melhor como nome do que alguma coisa terminada em `BR`.

## A definição que eu colocaria no README

> **Vernáculo is an open-source, self-hosted persona layer for AI agents.**
>
> Add regional language, conversational identity and sociolinguistic variation to AI applications without changing models, fine-tuning them or depending on Vernáculo infrastructure.
>
> Personas are portable files that run inside your application. Bring your own AI provider — or run completely locally.

E eu usaria algo como:

```text
VERNÁCULO
Local language. Local identity. Any AI.
```

Essa versão do projeto eu acho **consideravelmente melhor** que a proposta de um MCP isolado. MCP, OpenAI Skills, Claude, Gemini etc. passam a ser **targets/adapters do Vernáculo**. O patrimônio do projeto são a especificação aberta, os packs regionais, o compiler e os evals — tudo executável por quem baixar, sem você ter que bancar um servidor.

Eu faria o **Vernáculo praticamente inteiro em TypeScript**, mas com uma separação importante: **o formato das personas não pertence ao TypeScript nem a nenhum provedor**. Ele será composto de YAML + Markdown + JSON Schema. Assim, uma persona continua utilizável mesmo sem instalar nosso SDK.

### Stack definitiva

| Parte | Tecnologia |
|---|---|
| Linguagem | **TypeScript** |
| Runtime de desenvolvimento | **Node.js LTS** |
| Monorepo | **pnpm workspaces** |
| Formato das personas | **YAML + Markdown** |
| Schema oficial | **JSON Schema** |
| Validação em TS | **Zod 4** |
| CLI | **TypeScript + Commander + @clack/prompts** |
| Testes | **Vitest** |
| Lint/format | **Biome** |
| Build dos packages | **tsdown** |
| CI/CD | **GitHub Actions** |
| Releases | **Changesets + npm + GitHub Releases** |
| Primeiro provider | **OpenAI Responses API / Agents SDK** |
| Skills | **Agent Skills / `SKILL.md`** |
| MCP | **MCP TypeScript SDK v2**, posteriormente |
| Infraestrutura | **nenhuma** |
| Banco | **nenhum** |
| Backend Vernáculo | **nenhum** |

O uso de TypeScript também nos deixa perfeitamente alinhados com o ecossistema atual: o Agents SDK oficial da OpenAI tem implementação TypeScript, e o MCP TypeScript SDK v2 já é a linha estável que implementa a especificação MCP de 28 de julho de 2026. :chatgpt-content-reference{index="0"}

### `@vernaculo/core`

Esse é o coração e **não conhece OpenAI, Claude, Gemini ou MCP**.

```ts
import {
  loadPersona,
  resolvePersona,
  validatePersona,
} from "@vernaculo/core";

const persona = await loadPersona("pt-BR/ba/salvador");

const resolved = resolvePersona(persona, {
  intensity: 0.3,
});
```

Ele cuida somente de herança, composição, intensidade, validação e resolução dos arquivos.

Isso é deliberadamente pequeno.

## O formato é mais importante que o SDK

Uma persona seria aproximadamente:

```yaml
apiVersion: vernaculo.dev/v1
kind: Persona

metadata:
  id: pt-BR/ba/salvador
  name: Salvador
  language: pt-BR
  country: BR
  state: BA
  locality: Salvador

regionality:
  defaultIntensity: 0.30

linguistics:
  vocabulary:
    preferred: []
    contextual: []
    discouraged: []

  discourse:
    markers: []

  morphosyntax:
    patterns: []

  pragmatics:
    greetings: []
    acknowledgements: []
    closings: []

constraints:
  avoidCaricature: true
  avoidStereotypes: true
  preserveParentRole: true
  preserveTaskAccuracy: true

provenance:
  sources: []
```

E o JSON Schema vai definir formalmente o que é ou não uma persona Vernáculo.

Assim, amanhã alguém pode escrever um parser em:

```text
Python
Rust
Go
Java
C#
```

sem depender do nosso código TypeScript.

**Esse ponto é muito importante para um padrão open source.**

# E o compiler?

Teremos:

```text
persona.yaml
      ↓
@vernaculo/compiler
      ↓
Intermediate Persona Representation
      ↓
      ├── OpenAI instructions
      ├── SKILL.md
      ├── plain Markdown
      ├── Claude instructions
      ├── Gemini instructions
      └── MCP resource
```

Algo como:

```ts
const compiled = compile(persona, {
  target: "openai",
  intensity: 0.30,
  register: "customer-service",
});
```

O resultado poderia ser:

```ts
{
  instructions: "...",
  metadata: {
    persona: "pt-BR/ba/salvador",
    version: "1.0.0"
  }
}
```

O ponto-chave é:

**o compiler não chama IA.**

Portanto custa:

> **R$ 0.**

É basicamente transformação determinística de dados.

# O adapter OpenAI

Eu teria:

```ts
const openai = new OpenAI();

const response = await openai.responses.create({

  `,

```

A API key continua sendo:

```text
OPENAI_API_KEY do usuário
```

e nunca nossa.

# E eu separaria OpenAI de OpenAI Agents

Teríamos conceitualmente:

```text
@vernaculo/openai
```

para Responses API.

E talvez:

```text
@vernaculo/openai-agents
```

para quem usa:

```ts
import { Agent } from "@openai/agents";
```

porque o Agents SDK oficial roda dentro da própria aplicação do desenvolvedor e é especificamente indicado para casos em que o servidor do cliente controla deployment, tools, estado etc. :chatgpt-content-reference{index="1"}

Então:

```ts
const agent = new Agent({
  name: "Honda Salvador",

  instructions: vernaculo.instructions,

```

Mas eu **não colocaria `@openai/agents` dentro do core**.

# Agent Skills deve entrar já no MVP

Isso eu mudaria em relação ao que falamos anteriormente.

Eu implementaria o exporter de Skill **logo na v0.1**.

O padrão Agent Skills atualmente é extremamente simples: uma skill é um diretório contendo obrigatoriamente um `SKILL.md`, podendo possuir scripts, referências e assets adicionais. :chatgpt-content-reference{index="2"}

Então:

```bash
vernaculo export pt-BR/ba/salvador --target skill
```

poderia gerar:

```text
salvador-persona/
├── SKILL.md
├── references/
│   ├── vocabulary.md
│   ├── discourse.md
│   ├── pragmatics.md
│   └── sources.md
└── assets/
    └── examples.yaml
```

A pessoa pega essa pasta e joga no projeto/agente dela.

**Não precisa nem instalar `@vernaculo/core`.**

Essa é uma propriedade excelente do projeto.

em Rust e gerar bindings.
